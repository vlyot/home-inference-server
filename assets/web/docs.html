Quick Start

All inference requests go to POST /v1/infer with a JSON body. The server runs on http://localhost:8080 by default.

Text prompt

curl -X POST http://localhost:8080/v1/infer \
  -H "Content-Type: application/json" \
  -d '{
    "modality": "text",
    "text_input": { "prompt": "Hello, world!" }
  }'

Chat messages

curl -X POST http://localhost:8080/v1/infer \
  -H "Content-Type: application/json" \
  -d '{
    "modality": "text",
    "system_prompt": "You are a helpful assistant.",
    "text_input": {
      "messages": [
        { "role": "user", "content": "What is 2 + 2?" }
      ]
    }
  }'

Vision (image → text)

modality: "vision" is served by a two-stage pipeline: a small vision model (SmolVLM2 500M) produces an exhaustive literal description of the image, then a text tier answers your prompt over that description — see How vision works below. Send the image as image_base64 (raw base64, no data-URI prefix). image_url is not supported and returns 400. prompt is required.

IMG=$(base64 -w0 photo.jpg)
curl -X POST http://localhost:8080/v1/infer \
  -H "Content-Type: application/json" \
  -d "{
    \"modality\": \"vision\",
    \"vision_input\": {
      \"image_base64\": \"$IMG\",
      \"prompt\": \"What is the total amount on this receipt?\"
    }
  }"

A vision request may also carry response_format (see Structured Output) — the schema is applied to the reasoning stage, so you can ask for a JSON object describing the image.

Structured Output (JSON mode)

Add response_format to any request that uses text_input.messages (the chat path). It is forwarded verbatim to llama-server, which compiles it to a sampling grammar — the model cannot emit a token that breaks the shape, so no retry loop is needed. The client just parses output as JSON.

Two forms, matching the OpenAI API:

// 1. JSON Schema — strongest guarantee, recommended
"response_format": {
  "type": "json_schema",
  "json_schema": {
    "name": "person",
    "schema": {
      "type": "object",
      "properties": { "name": {"type": "string"}, "age": {"type": "integer"} },
      "required": ["name", "age"]
    }
  }
}

// 2. Loose "just valid JSON"
"response_format": { "type": "json_object" }
curl -X POST http://localhost:8080/v1/infer \
  -H "Content-Type: application/json" \
  -d '{
    "modality": "text",
    "text_input": { "messages": [
      { "role": "user", "content": "Give me a person named Alice, age 30." }
    ]},
    "response_format": { "type": "json_schema", "json_schema": {
      "name": "person",
      "schema": { "type": "object",
        "properties": { "name": {"type":"string"}, "age": {"type":"integer"} },
        "required": ["name","age"] } }
  }'
# -> {"output": "{\"name\": \"Alice\", \"age\": 30}", ...}

Notes:

  • Handled entirely server-side. The client sends the schema and parses the string in output — nothing else to implement.
  • Prompt-only requests (text_input.prompt) ignore response_format. Use messages.
  • Grammar-constrained decoding is slightly slower per token, and a very small model can occasionally produce valid-but-thin output when a schema is tight.
  • A schema llama-server cannot compile returns 400 {"code": "invalid_grammar"} with the reason in message.
  • The reasoning-capable strong tier (gemma-4-e4b) may spend its whole token budget "thinking" before the JSON — give it a generous max_tokens, or pin a non-reasoning tier with preferred_tier.

Streaming (SSE)

curl -N -X POST http://localhost:8080/v1/infer \
  -H "Content-Type: application/json" \
  -d '{
    "modality": "text",
    "text_input": { "prompt": "Tell me a short story." },
    "stream": true
  }'

Request Reference

POST /v1/infer — body: application/json

InferRequest

Field Type Default Description
correlation_id string auto Caller-supplied tracing ID, propagated through every log event and response. If omitted, the server generates one ("req-" + UUID4 without hyphens).
modality string required Inference modality. Must be "text" or "vision".
text_input TextInput — Required when modality = "text". See TextInput below.
vision_input VisionInput — Required when modality = "vision". See VisionInput below.
max_tokens integer 0 (server default) Maximum output tokens to generate. 0 (the default) means: for a request carrying text_input.messages (chat-completions endpoint), the server tokenizes the conversation, reads the loaded model's context size, and uses whatever is actually left in the context window (minus a 10% safety margin) — so a reasoning-capable model's "thinking" tokens (see Streaming Guide) get the full remaining budget instead of an arbitrary cap. Falls back to a fixed 2048 if that introspection fails. For a plain text_input.prompt (single-shot completion endpoint, no chat template, no reasoning), 0 uses a fixed 512.
temperature float 0.0 (server default) Sampling temperature. Higher = more random. 0.0 uses the server default.
system_prompt string "" Convenience shorthand — equivalent to prepending a role=system message. Ignored if text_input.messages already contains a system entry.
stream boolean false When true, response is text/event-stream (SSE). See Streaming Guide.
timeout_ms integer 0 (server default) Caller-specified deadline in milliseconds. Returns 408 timeout if exceeded. 0 uses the server default — 600 000 ms, overridable with the HIS_INFER_TIMEOUT_MS env var. There is always a deadline; a hung backend cannot block indefinitely.
priority string "normal" Urgency level. Controls speed-floor enforcement and (for "high") bypasses deferral, triggering an X-Quality-Degraded: true header when served on the Weak tier. Values: "high" | "normal" | "low". "low" has no speed floor.
min_tier string "weak" Quality floor. If the router would select a tier below this value, the request is overloaded (429) rather than served degraded. Values: "strong" | "mid" | "weak".
preferred_tier string "" (automatic) Pins tier selection to exactly this tier instead of the default "largest tier that fits in free VRAM" — e.g. deliberately running the small model to leave VRAM headroom for other GPU work. Values: "strong" | "mid" | "weak". Unlike min_tier (a floor, never upgraded away from), this is an exact pin: it evicts a larger already-loaded model if needed, and the speed-floor cascade never overrides it. An unrecognized value returns 400 invalid_request. Backs the model-tier dropdown in the built-in Chat UI at GET /chat. For a vision request this pins the reasoning tier; the perception model (SmolVLM2) is fixed.
response_format object null (unconstrained) Constrains output to a JSON shape. Forwarded verbatim to llama-server, which compiles it to a sampling grammar so the model cannot emit a non-conforming token. Accepts {"type":"json_object"} or {"type":"json_schema","json_schema":{...}} (OpenAI shape). Requires text_input.messages — ignored on a prompt-only request. On a vision request it is applied to the reasoning stage. A schema llama-server cannot compile returns 400 {"code":"invalid_grammar"}. See Structured Output.

TextInput

Exactly one of prompt or messages must be set.

FieldTypeDescription
prompt string Single-turn completion prompt. Mutually exclusive with messages.
messages ChatMessage[] Full multi-turn conversation history. Mutually exclusive with prompt. The entire array is sent to the model's chat-completions endpoint every request (the model itself is stateless), so resend the whole conversation each turn. The combined transcript plus the reply must fit the model context window (n_ctx, 4096 for the current roster) — when it overruns, the server silently drops the oldest turns. See ChatMessage below.

ChatMessage

FieldTypeDescription
role string Speaker role. Values: "system" | "user" | "assistant".
content string Message text.

VisionInput

image_base64 and prompt are required.

FieldTypeDescription
image_base64 string Raw base64-encoded image bytes (no data: prefix). JPEG, PNG, WebP and GIF are recognised. Required.
image_url string Not supported. Sending it returns 400 invalid_request ("image_url is not supported; send the image as image_base64"). Fetch the image yourself and send image_base64.
prompt string Required. The question or instruction about the image. This is answered by the reasoning stage over the perception model's description — see How vision works.

StreamChunk (streaming mode)

Each SSE event carries one StreamChunk JSON payload. The final chunk has done: true and populates the summary fields. See the Streaming Guide for consumption details.

FieldTypeNotes

correlation_id string Caller-supplied or generated correlation ID.

reasoning string Omitted when empty. Partial chain-of-thought text from a reasoning-capable model (e.g. Gemma's "thinking" mode). Mutually exclusive with delta on any given chunk — never both set. One of the error codes; delta and the summary fields are empty in that case. Omitted on success.

Images in chat. The chat UI has a 📎 attach button. On attach it calls POST /v1/describe, then folds the description into the conversation as a hidden turn — so the image is answered by a normal streaming text request and every follow-up keeps the image in context without re-running vision. The image thumbnail is shown in the live session but not persisted; a reloaded chat shows an [image attached] placeholder, and follow-ups still work because the description turn is saved.

Running on a LAN

The local API is unauthenticated by default. To expose it beyond localhost, set:

Env varEffect
HIS_API_KEYWhen set, non-loopback callers to /v1/* must send X-API-Key: <value> (loopback is exempt — the dashboard/chat keep working locally). Missing/wrong key → 401.
HIS_CORS_ORIGINSComma-separated allow-list of browser Origins. When set, matching origins get Access-Control-* headers and OPTIONS preflight is answered. Unset = no CORS (same-origin only).
HIS_BIND_ADDRListen address; default :PORT (all interfaces). Set 127.0.0.1:8080 to keep it local-only.
HIS_INFER_TIMEOUT_MSPer-request inference deadline when timeout_ms is omitted. Default 600000.
HIS_MAX_PARALLELConcurrent-inference degree: the llama-server --parallel value, the worker-pool size, and the backend semaphore capacity. Default 2. Sized for an 8 GB card; raising it needs VRAM for one more KV cache per tier.
HIS_CTX_SIZEllama-server --ctx-size (shared across the --parallel slots). Default 4096; the roster's KV estimates are tuned for this value.

The Chat UI renders assistant replies as markdown (headers, bold/italic, lists, tables, code blocks, blockquotes) using two vendored, embedded libraries served from GET /vendor/* — marked (markdown → HTML) and DOMPurify (HTML sanitizer, strips scripts/event handlers/javascript: URLs from the parsed output before it reaches the DOM, since the HTML originates from model output, not a trusted source). Both are bundled in the binary; nothing is fetched over the network at runtime — the Chat UI works fully offline.

Admin / maintenance

A small loopback-only control surface for pausing and restarting the server without killing the process. Every /v1/admin/* endpoint returns 404 to a non-loopback caller, so it is invisible from the LAN even when the API itself is exposed. No key — being on 127.0.0.1 is the whole gate.

CallEffect
GET /v1/adminState probe: {"state", "in_flight", "queue_depth"}. No side effect.
POST /v1/admin/drainEnter draining: new POST /v1/infer (blocking and streaming) returns 503 {"code":"draining"}; the offline-queue worker stops claiming new relay jobs. Requests already in flight finish normally, and every read-only endpoint (/healthz, /v1/status, /v1/logs, /v1/chats*, /v1/tokenize) keeps working. Idempotent.
POST /v1/admin/resumeLeave draining: inference is served again, the offline worker resumes claiming.
POST /v1/admin/restartDrain, then run the normal 15 s shutdown (stop HTTP, evict the model, kill llama-server), write a restart.flag next to the executable, and exit 0. On the standard Windows deploy, run.cmd is a loop that sees the flag and relaunches the binary (picking up a freshly staged build). Returns 501 if the process was not started with a restart channel (only cmd/server wires one). A deliberate Stop-ScheduledTask kills the whole tree, so the loop cannot outlive an intentional stop.

While draining, GET /healthz and GET /v1/status report "state": "draining" — /healthz stays 200 (liveness), the field is the readiness signal. Drain does not auto-expire; it persists until /v1/admin/resume or a restart. The read-only dashboard at GET / shows a "Draining" banner while this is set.

The GET /admin browser page is a button UI for these same three calls — same loopback restriction (it will not work from another device). It is the GUI equivalent of the curl -X POST http://localhost:PORT/v1/admin/* examples.

Streaming Guide

Set "stream": true in the request body. The response will be Content-Type: text/event-stream (Server-Sent Events). Each event is a JSON-encoded StreamChunk prefixed with data: .

Event format

data: {"request_id":"...","correlation_id":"...","delta":"Hello","done":false}

data: {"request_id":"...","correlation_id":"...","delta":" world","done":false}

data: {"request_id":"...","correlation_id":"...","delta":"","done":true,"tokens_generated":42,"tokens_per_sec":11.3,"queue_wait_ms":2,"inference_ms":3710,"duration_ms":3712,"model_tier":"strong"}

data: [DONE]

The stream ends with a literal data: [DONE] line after the final chunk.

If inference fails mid-stream, the final chunk instead carries an error field (e.g. {"...","done":true,"error":"overloaded"}) with no summary fields, followed by data: [DONE]. Check chunk.error before treating a done chunk as success. A completion that returns no backend error but yields zero content and zero reasoning also terminates with "error":"internal_error" rather than an empty success chunk — a bare done chunk with no error always means at least one delta chunk was produced.

Reasoning models

A reasoning-capable model (e.g. Gemma's "thinking" mode) streams its chain-of-thought under a separate reasoning field on each chunk, never mixed into delta:

data: {"request_id":"...","correlation_id":"...","reasoning":"Let me think","done":false}

data: {"request_id":"...","correlation_id":"...","reasoning":" about this...","done":false}

data: {"request_id":"...","correlation_id":"...","delta":"The answer is 4.","done":false}

data: {"request_id":"...","correlation_id":"...","done":true,"tokens_generated":18,...}

data: [DONE]

Render reasoning chunks separately from delta chunks — the built-in Chat UI shows them in a collapsible "Thinking…" section that auto-collapses once the first delta chunk arrives, matching llama-server's own chat UI. A hard prompt can cause a reasoning model to spend its entire max_tokens budget thinking and never produce a visible answer; when that happens the stream ends with "error":"reasoning_exhausted" instead of a silent empty success (see Error Codes). The non-streaming POST /v1/infer response carries the same distinction via InferResponse.reasoning, separate from output.

JavaScript consumer example

const res = await fetch('/v1/infer', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    modality: 'text',
    text_input: { prompt: 'Tell me a story.' },
    stream: true,
  }),
});

const reader = res.body.getReader();
const decoder = new TextDecoder();
let output = '';

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  const text = decoder.decode(value, { stream: true });
  for (const line of text.split('\n')) {
    if (!line.startsWith('data: ') || line === 'data: [DONE]') continue;
    const chunk = JSON.parse(line.slice(6));
    if (chunk.error) throw new Error(chunk.error);
    if (chunk.delta) output += chunk.delta;
    if (chunk.done) console.log('Summary:', chunk);
  }
}
console.log('Full output:', output);
The streaming path bypasses the batcher and the worker pool — the request goes directly to the backend. It still contends for one of the max_parallel concurrent-inference slots (the same semaphore the pooled requests use), and shares the VRAM-tier selection and pressure-policy logic.

A stream: true vision request runs the perception hop blocking (no tokens stream during it), then streams the reasoning hop's deltas.

Pressure Policy

The server monitors VRAM headroom and CPU utilisation in real time. Under extreme load it defers a request to the hosted relay (the durable Railway queue) rather than overloading the model or dropping the request.

Deferral (enqueue-time check)

ConditionEffect
VRAM < 500 MB AND CPU > 90% (and a relay is configured) The request is forwarded to the relay's /enqueue. Response is 202 Accepted with {"deferred": true, "request_id": <relay job id>, "result_url": "<relay>/result/<id>"}. Poll result_url (see Remote Access) — it survives a PC restart. If the relay is unreachable at that moment the server returns 503 overloaded instead. With no relay configured (RAILWAY_QUEUE_URL unset) the server never defers — it serves, cascades tiers, or 503s from the local queue.
priority = "high" Always bypasses deferral. Served on Weak tier if necessary; response carries X-Quality-Degraded: true header.

A deferred job re-enters processing through the same offline-queue worker that drains F&F jobs — immediately once pressure clears, or after the PC restarts. There is no local defer queue and no local drain loop.

Idle eviction & external VRAM pressure

The loaded model is evicted after 20 s idle, on a tier switch, or when an external process claims enough VRAM that the model can no longer be reloaded. The external-pressure check compares free VRAM against the model's full GPU-resident footprint (weight + KV/compute overhead) plus that footprint added back — free VRAM reported by the driver already excludes the running model's own allocation, so the check asks "would this still fit if reloaded now?" rather than "is free VRAM below the raw weight size?". Eviction for external pressure also requires free VRAM to have fallen below an 800 MB absolute floor, so a model simply occupying most of the card is never mistaken for external contention. A model whose subprocess is mid-restart after a connection error is never evicted until the restart settles.

Speed floors

After each completed job the server updates a rolling tok/sec average for the loaded tier. Each sample is normalised for the number of requests that were running concurrently at the time (llama-server time-slices its --parallel slots roughly evenly), so the average tracks a single-stream-equivalent rate rather than sagging under load. If the observed speed drops below a priority floor, the router falls back to a lower-VRAM tier that can sustain the required throughput.

PriorityMinimum tok/sec
high8 tok/sec
normal4 tok/sec
lowno floor

Speed floors are only enforced once the rolling average has at least one sample — new model loads receive the benefit of the doubt.

Error Codes

All error responses have HTTP status codes and a JSON body with a machine-readable code field.

CodeHTTPCauseRecommended Action
invalid_request 400 Malformed JSON, missing required field, or empty prompt/messages. Fix the request body.
invalid_modality 400 modality is a non-empty value other than "text" or "vision". (A missing modality is invalid_request.) Use "text" or "vision".
invalid_grammar 400 response_format could not be compiled to a sampling grammar (malformed JSON Schema, unsupported construct). The reason from llama-server is in message. Fix the schema. Test it against a small request first.
not_implemented 501 A documented capability not wired up in this build. No modality currently returns this — both text and vision are implemented. Reserved for future specialist backends. n/a for the current roster.
unauthorized 401 Missing or invalid X-API-Key. On the local server only when HIS_API_KEY is set and the caller is not on loopback; also the relay's response to a bad credential. Send the correct X-API-Key (or a valid relay Bearer token).
overloaded 429 / 503 No tier can be loaded (not even CPU-only), a min_tier floor can't be met (429), or a deferral is needed but the relay is unreachable (503). Retry with exponential backoff, lower min_tier, or pick a smaller preferred_tier.
draining 503 A new POST /v1/infer arrived while the server is draining for maintenance (POST /v1/admin/drain). Read-only endpoints are unaffected. Retry after GET /healthz reports "state":"ok" again.
not_found 404 Remote relay only. GET /result/{id} — unknown id, another caller's job, or a result aged past RESULT_TTL_SECONDS. Check the id; fetch results within the TTL (default 1 h).
model_load_failed 503 The llama-server subprocess failed to start or load model weights. Check server logs; verify the model file exists.
internal_error 500 Unexpected server-side error. Check server logs.
reasoning_exhausted —† A reasoning-capable model spent its entire max_tokens budget on reasoning chunks and never produced a delta chunk. See the Streaming Guide. Retry, ask something more specific, or raise max_tokens.
unavailable 503 / 501 A backend or capability is not available: no backend for the modality, a wedged subprocess, or (501) /v1/tokenize / /v1/logs called before that feature is wired. Retry; check the server configuration and roster.
timeout 408 Inference exceeded timeout_ms or the server default (HIS_INFER_TIMEOUT_MS, 600 s). Retry or increase timeout_ms.
rate_limited 429 Remote relay only. Per-identity token bucket exhausted (~10 jobs/min). Back off a few seconds and retry.
quota_exceeded 429 Remote relay only. Per-identity daily job quota reached (~200/day). Wait until UTC midnight; the counter resets daily.
queue_full 503 Remote relay only. Pending queue depth is at its cap (~500) — the PC isn't draining fast enough. Retry later; the backlog clears as the PC processes it.

† reasoning_exhausted is stream-only — it never appears as an HTTP status or on POST /v1/infer without stream: true; it is only ever the error field of a streaming StreamChunk.

Model Roster

The server loads one model at a time. Text and vision each have their own tier list; the tables below are the text roster plus the vision tier. Every tier can run fully on GPU, split across GPU + system RAM, or entirely on CPU — the split is chosen at load time from current free VRAM.

How vision works (SmolVLM2 → Gemma pipeline)

A modality: "vision" request runs in two hops, and the two models are never loaded at the same time — so peak VRAM is only what the reasoning hop needs and the server still idles at ~0 VRAM.

  1. Perceive. SmolVLM2 500M is loaded (its weights + vision projector, <1 GB) and asked not your question but a fixed instruction: produce an exhaustive, literal inventory of everything in the image — all text and numbers verbatim, objects, layout, colours. Then its subprocess is shut down and its VRAM freed.
  2. Reason. That description is handed to the ordinary text roster as a normal chat request: a system turn explaining "you can't see images, here is a description", then your prompt. So tier selection, the speed-floor cascade, min_tier, preferred_tier, deferral and response_format all apply to this hop unchanged.

Latency: roughly 10–25 s fully cold (two model loads), a few seconds when a text tier is already warm from recent traffic.

Degradation: if VRAM pressure is so high that no text tier can load at all, the request returns SmolVLM2's raw description as the answer with X-Quality-Degraded: true rather than failing. Extreme pressure (< 500 MB VRAM AND > 90% CPU) defers like a text request.

Trade-off: the reasoning model only ever sees SmolVLM2's text, never the pixels — whatever the perception hop omits, the answer can't recover. For most "what does this show / what's the number / summarise this" questions that is fine; pixel-exact tasks are weaker than a natively-multimodal model would be.

This is a general pipeline backend: a future audio or OCR modality is added by registering another perceive→reason pipeline with a different perception model and prompt — the core request path does not change. See Specialist Backends.

Tier selection algorithm

Per request, on the roster for the request's modality:

  1. Pinned tier (if preferred_tier is set). Skip steps 1–3 entirely — load exactly the requested tier, evicting a different already-loaded tier if needed. Never cascades away from it, even if that tier fails the speed floor.
  2. Fit, largest first. For each tier (largest weight first) compute the GPU/CPU layer split for current free VRAM, then the GPU-resident footprint (on-GPU weight fraction + the model's non-weight overhead). The non-weight overhead is KVCacheMB × N + KVFixedMB, where N is max_parallel (the concurrent-inference degree, default 2) — each of llama-server's --parallel slots holds its own KV cache, while the compute buffers and CUDA context are counted once. Admit the first tier whose footprint + 10% buffer fits.
  3. CPU fallback. If no tier fits any GPU layers, load the smallest tier whose non-weight overhead alone fits, with all weights in system RAM.
  4. Speed-floor cascade. If the chosen tier's rolling tok/sec is below the priority floor (high = 8, normal = 4, low = none), drop to the next-smaller tier and re-select. min_tier caps how far this can drop; a request pinned to a tier it can't speed-satisfy is served there (degraded) rather than failing.
  5. OOM cascade. If the chosen tier's subprocess actually fails to load (CUDA OOM at spawn), it is evicted and the next-smaller tier is tried — bounded by min_tier and skipped for a preferred_tier pin.
  6. Deferral. If free VRAM < 500 MB AND CPU > 90% and a relay is configured, the request is handed to the relay (202, see Pressure Policy) unless priority = "high".
  7. Overloaded. Returned when not even a CPU-only load of the smallest tier fits, when min_tier can't be met, or when a deferral is needed but the relay is unreachable.

The active split is visible on GET /v1/status as loaded_model.gpu_layers / total_layers (-1 = full GPU, 0 = CPU-only) and on the dashboard's Active Tier card.

Subprocess lifecycle

Each tier runs as a managed llama-server subprocess, spawned with --parallel N --cont-batching (N = max_parallel, from HIS_MAX_PARALLEL, default 2) so one process serves up to N requests concurrently via continuous batching. A bounded worker pool of N workers feeds it; a semaphore inside the backend is the hard ceiling and also gates the streaming path. Evicting a model (20 s idle, tier switch, or VRAM pressure) shuts its subprocess down so it stops holding VRAM and RAM. A port-scoped reaper additionally kills any stray llama-server left on a roster port by a previous crash — on startup and whenever nothing is loaded. On Windows each subprocess is placed in a kill-on-close job object, so the whole tree dies even if the server is force-killed.

GET /v1/status and GET /v1/status/pressure report self_vram_mb (VRAM held by the server's own subprocesses) and, when total VRAM is known, other_vram_mb (what other applications are using).

Remote Access (Hosted Relay)

Apps that aren't on this machine's network — phones, friends-and-family devices, browser web apps — don't call this server directly. They call a hosted relay on Railway that queues jobs in Postgres. This PC makes only outbound long-poll connections to the relay, claims jobs, runs them through the same local pipeline, and posts results back. If the PC is offline the job waits in the queue and drains on the next reconnect — the app polls either way and never has to know.

The relay's base URL is your Railway service URL, not localhost. The local /v1/* API on this page is unchanged and still only reachable on the LAN.

Authentication

Every relay request carries either header:

  • Authorization: Bearer <token> — a Neon Auth access token. The app signs the user in with the Neon Auth (Stack Auth) client SDK — magic link or OAuth, hosted by Neon, no email server of your own — and forwards the token it gets back. The relay verifies it against Stack Auth's published JWKS (ES256).
  • X-API-Key: <key> — the static relay key. For native apps, CLI tools, and the PC worker.

Both resolve to an identity that scopes result retrieval and drives the per-identity rate limit and daily quota. Missing or invalid credentials return 401 unauthorized; a valid Neon Auth token whose user has not been added to the relay's invite list returns 403. Either way nothing is written first.

You do not deploy or proxy an auth server. Neon Auth (Stack Auth) hosts sign-in, the magic-link / OAuth email, token issuing, and token refresh at api.stack-auth.com. Your app talks to it directly with the client SDK; the relay only ever sees the finished token.

3. Call the relay with the token

async function infer(prompt) {
  const { accessToken } = await user.getAuthJson();   // SDK refreshes it as needed
  const enq = await fetch(`${RELAY_URL}/enqueue`, {
    method: "POST",
    headers: {
      "Authorization": `Bearer ${accessToken}`,
      "Content-Type":  "application/json",
    },
    body: JSON.stringify({
      correlation_id: crypto.randomUUID(),
      payload: { modality: "text", text_input: { prompt } },
    }),
  });
  if (enq.status === 403) throw new Error("you're not on the invite list yet");
  const { id } = await enq.json();

  // poll until terminal
  for (;;) {
    const r = await fetch(`${RELAY_URL}/result/${id}`, {
      headers: { "Authorization": `Bearer ${accessToken}` },
    });
    const body = await r.json();
    if (body.status === "done")   return body.result_payload.output;
    if (body.status === "failed") throw new Error(body.error_code);
    await new Promise(res => setTimeout(res, 1500));   // pending → PC busy or asleep
  }
}

Check GET /status first if you want to show "PC is offline, this will process later" before the user submits.

  -H "Authorization: Bearer $TOKEN" \

# -> {"status":"done","result_payload":{"output":"Hi there!", ...}}

A status of pending for a while just means the PC is asleep — show "will process when the PC is back online" and keep polling. Results are purged from the relay ~1 hour after completion.

Membership (invite-only)

Neon Auth's sign-up is open — anyone can create an account — but that alone gets a caller nothing. The relay rejects (403 "not an invited member") any token whose Stack Auth user id is not in its allowed_members table. Neon Auth mirrors every account into the relay's database as neon_auth.users_sync; memberadd looks a person up there by email (so they must have signed in at least once) and adds them:

DATABASE_URL=… go run ./cmd/memberadd -email them@example.com            # add
DATABASE_URL=… go run ./cmd/memberadd -email them@example.com -remove    # revoke
DATABASE_URL=… go run ./cmd/memberadd -list                             # show the list

Onboarding order for a new person: they open the app and sign in once → you run memberadd -email … → their next request succeeds.

How the relay verifies a token

On the first Bearer request the relay fetches Stack Auth's public keys (JWKS) and caches them. Per request it then: checks the JWT is ES256 (rejects alg:none), verifies the signature against the cached key for the token's kid (refetching once if the key id is new — key rotation), checks the issuer is this project and the token is unexpired, then looks the subject up in allowed_members. A forged token — even one with a real-looking kid and the correct issuer — fails the signature check and gets 401.

Privacy: every prompt and completion that goes through the relay — including a request the local server deferred under pressure — is written to the relay's Postgres (Neon) and is readable by anyone with database access until the TTL sweep (RESULT_TTL_SECONDS, default 1 h). Payloads are not encrypted at rest. Don't send secrets through the relay path.

Specialist Backends

The router dispatches by modality string to a registered backend. Additional specialist backends — code completion, embeddings, speech-to-text — can be registered as new modality keys without changing the request/response contract or the core pipeline (queue → batcher → dispatcher → router).

Two extension shapes exist:

  • A plain backend — one model behind the backend.Backend interface, registered under its own modality string (how the text roster works).
  • A pipeline backend — a backend that itself orchestrates a perceive sub-backend and a reason sub-backend, evicting the first before running the second so they never share VRAM (how vision works — see How vision works). An audio modality (a speech model perceiving → a text tier reasoning), or an OCR specialist, is added the same way: a new pipeline with a different perception model and prompt.

When a specialist backend is added it will be documented here with its modality string, accepted input fields, and response shape. Requests for an unregistered modality return 503 unavailable.

Registered in the current build: text (tiered roster) and vision (SmolVLM2 → Gemma pipeline). Audio is not — the Gemma 4 audio encoder is not yet functional in llama.cpp.
